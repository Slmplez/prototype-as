## Exact Selection

A new formal has no existing alias. Selection therefore uses only the method's
diagram and native alias. Python and the fixed native method resolver both reject
ambiguous aliases and foreign owners. They do not borrow another formal's alias
or select a method by name/ordinal. The native creation template receives typed
values as Cebra parameters; agent strings never become executable Smalltalk.

Preview re-observes the complete recorded owner/configuration baseline, validates
the native method, argument name and profile, and probes existing recovery keys
and capacity. It lists one planned input pin per exact Class occurrence, including
nested caller scopes, plus existing pin layout candidates. The new formal/pin
aliases are assigned only by actual native creation and are not predicted.

The `validate` branch returns before accessing the allocating recovery registry.
Preview does not call setters, prepare recovery, reserve request IDs or publish
an edit WAL. A supported complete preview reports `write_eligibility=prepare_required`;
execution must still recheck. A restoration hold reports
`DATABASE_RESTORATION_REQUIRED`. If native acceptance is disabled, preview reports
`NATIVE_CREATION_NOT_ACCEPTED` and actual creation refuses before intent/setters.

## Native Execution And Journal

Recovered `EtasAPIDiscreteMethod>>addArgumentElement:modelType:` checks duplicate
names, creates the model template, appends a method argument, calls `modified`
and `autoCommitDatabase`. This declaration operation alone does not reliably
materialize stable graphical pins in each caller. The complete executor prepares
original signature and all owner graphs first, then journals these exact steps:

1. `signature_apply / create_argument` on the exact Class definition.
2. `store_i / apply` on each prepared owner, including the definition.
3. An actual complete-owner after observation and retained native material.
4. Separate inverse preflight, `signature_restore`, owner restores in reverse
   order, actual restored observation and release.

Creation has no prune steps. Both the Python WAL auditor and the C# retained
loader implement this plan and refuse a deletion command in a creation journal.
Unknown signature/store outcomes keep their journal and quarantine; no automatic
mutation replay is introduced. The native inverse still requires the complete
exact-after baseline and original objects in the same process. It is not the
pending local inverse that preserves unrelated later changes.

## Effect Validation

`bd_class_creation.creation_effects` checks the actual new formal alias, appended
index, exact name/type/owner/direction, independent public signature, unchanged
persisted configuration and exactly one unique new input pin per caller occurrence.
It rejects unrequested nodes/data connections. It then reverses the recorded
observations into the existing closed-removal validator to check every collected
scope and unrelated field, including explicit public/native layout displacement.
This reuse is a validation reduction, not an execution or reconstruction method.

Synthetic effect/protocol tests do not establish online creation or native
restoration. Positive creation/inverse, three independent fixtures, faults,
shared-owner/type boundaries, UI lifecycle and final AEB_Core/FLOW remain required.
The original display01 hold and restoration problem remain separate.

Signature, configuration and collected graph comparisons use JSON fingerprints.
Boolean `true` and integer `1` are distinct; Python numeric equality cannot make
a changed field satisfy an exact creation or inverse guard.
